开始之前：5 个基础概念

后面的每个问题都会用到这些概念，先花两分钟建立共同语言。

① ORM：用 Python 类描述数据库表

ORM（对象关系映射）= 把数据库的表翻译成编程语言里的类。
models.py 里的 class Employee(Base) 就对应数据库里的 employee 表；类的属性对应表的列。你操作 Python 对象，SQLAlchemy 在背后帮你生成 SQL 语句发给 PostgreSQL。

② Alembic：数据库的"版本控制"

代码用 Git 管版本，数据库结构用 Alembic 管版本。alembic upgrade head = 把库升级到最新结构；downgrade base = 退回空白库（删光所有表）。当前版本号记录在数据库里一张叫 alembic_version 的小表中。

③ 真源（Single Source of Truth）

同一个事实只允许存在一份"权威定义"，其他地方都从它派生。这个项目里"表长什么样"有三份独立描述：models.py、alembic 迁移文件、手写 SQL 文件——人改了其中一份忘了另一份，就叫"漂移（drift）"。问题 #1 就是漂移的实例。

④ 默认值有两个层次，很容易混淆

写法谁生效
default=dict只有通过 SQLAlchemy 插入数据时，Python 在内存里先填上值
server_default写进表结构（DDL），任何方式插入（包括 psql 手敲 SQL）都生效
onupdate=func.now()同样只是 ORM 层，只有通过 SQLAlchemy 更新才触发

⑤ 数据库约束家族

约束管什么
UNIQUE这列（或列组合）的值不能重复——只比"相等"
CHECK值必须满足一个表达式，如 amount >= 0
FOREIGN KEY值必须存在于父表里，防"孤儿数据"
EXCLUDE（排他）范围之间不能"相交"——UNIQUE 做不到的它能做
触发器 Trigger插入/更新/删除前后自动执行的自定义逻辑，表达力最强

⑥ CWD：程序眼中"我在哪"

CWD = 当前工作目录 = 你运行命令时所在的目录，而不是代码文件所在的目录。代码里写相对路径 ".env"，找的其实是 CWD 下的 .env。同一个程序，从不同目录启动，行为可能完全不同。

#1 两份"建表图纸"细节已经对不上了（schema 漂移）

涉及：backend/alembic/versions/0001_initial_schema.py:106 · backend/sql/001_initial_schema.sql · backend/src/paylite/db/models.py

大白话

装修时施工队拿图纸 A 干活（Alembic 迁移实际是调用 models.py 的 create_all 建表），你自己留档的图纸 B 是手写 SQL 文件，文件开头还写着"两者必须保持行为等价"。但现在两份图纸已经不一致了——JSONB 列的默认值、updated_at 的自动刷新、表和列的中文注释（COMMENT），SQL 文件里有、模型里没有（或者反过来）。

具体差异（4 处）

# models.py —— Alembic 真正用来建表的
field_mapping = mapped_column(
    JSONB, nullable=False,
    default=dict   # ← 只有 Python 插入时才生效
)

# sql/001_initial_schema.sql —— 留档审查的
field_mapping JSONB NOT NULL DEFAULT '{}'::jsonb
#                    ↑ 写进了表结构，谁插入都生效

同类差异还有 3 处：formal_status 的 DEFAULT FALSE、updated_at 的自动更新（模型靠 ORM 的 onupdate，SQL 侧没有触发器）、6 条 COMMENT ON 语句。

会发生什么

真实后果：用 Alembic 建出来的库，没有 JSONB 默认值——将来用 psql 手工 INSERT 一行会直接报 NOT NULL 错误；用 SQL 文件建的库，绕过 ORM 更新数据时 updated_at 不会刷新，审计时间不准。

更隐蔽的：以后用 alembic revision --autogenerate 生成新迁移时，它拿模型和数据库做对比，会把"模型与 SQL 文件的差异"当成新变更，生成莫名其妙的迁移。

知识点：真源（概念③）· create_all 是"照着模型一键建所有表" · ORM 层默认值 vs DDL 层默认值（概念④）。
修法：二选一——模型补齐 server_default 和 comment=，或迁移改成显式 op.create_table 以 SQL 文件为准。核心是只留一份真源。

#2 跑一次集成测试，可能把开发数据全部删光

涉及：backend/tests/test_postgres_integration.py:50

大白话

测试结束后有个"打扫现场"的动作：command.downgrade(alembic_config, "base")。base 的意思是"退回到没有任何表的初始状态"——也就是删光全部表。测试代码假设你给它的 URL 一定指向一次性的测试库，但它没有任何检查，你给什么它删什么。

# tests/test_postgres_integration.py
TEST_DATABASE_URL = os.getenv("PAYLITE_TEST_DATABASE_URL")

@pytest.fixture(scope="session")
def postgres_engine():
    command.upgrade(alembic_config, "head")    # 建所有表
    yield engine
    command.downgrade(alembic_config, "base")  # ← "base" = 删光所有表，无确认、无回收站
真实后果：手滑把 PAYLITE_TEST_DATABASE_URL 填成开发库 paylite → 跑一次测试 = 本地所有工资数据清空。没有弹窗，没有提示。
知识点：upgrade / downgrade 是一对对称的破坏性操作；测试隔离原则——测试必须永远指向专门的库；防御性编程——代码要假设使用者会犯错，URL 校验就是安全带。
修法：fixture 开头加检查（比如拒绝库名为 paylite、或要求 URL 以 _test 结尾），并在 README 写明测试库约定。

#3 生效区间可以"重叠"，查询会出现两条"当前有效"记录

涉及：backend/src/paylite/db/models.py:159,191,216,241,421,464,490（employee_assignment / employee_salary / employee_bank_account / employee_base / social_security_rule / housing_fund_rule / attendance_rule 共 7 张表）

大白话

调薪、调岗这类记录都是"从某天到某天有效"的区间数据。现在的约束只挡了一种错误：同一个员工从同一天开始出现两条记录。但它挡不住下面这种：

记录 A
2026-01-01 起，结束日为空 = 一直有效
记录 B
2026-02-01 ── 2026-03-01
⚠ 2026 年 2 月任何一天，两条记录同时"有效"。问"员工 2 月 15 日的工资是多少"→ 系统拿到两个答案。

为什么会漏？因为 UNIQUE 只会比较"值相不相等"，不会比较"区间相不相交"。这正是排他约束（EXCLUDE）存在的意义。

建议的约束写法

-- 先启用扩展（btree_gist 让 gist 索引支持"等于"比较）
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE employee_salary ADD CONSTRAINT ck_employee_salary_no_overlap
EXCLUDE USING gist (
    employee_id WITH =,                       -- 同一员工
    daterange(effective_from, effective_to) WITH &&   -- 的日期区间不能相交(&&)
);
真实后果：工资计算要读"员工当前工资"，重叠区间让这个查询返回 2 行——程序要么报错，要么随机挑一条，工资算错且难复现。而工资恰是这个系统最不能错的东西。
知识点：概念⑤里的 EXCLUDE 排他约束 · daterange 把两个日期变成一个"区间值" · && 是"相交"运算符 · 涉及这 3 张表的都是工资计算的关键输入（薪酬、城市规则、考勤规则）。

中优先级（#4 – #8）

不致命，但会造成数据不一致或部署时的隐性坑，建议随业务代码一起处理。

#4 工资记录上的冗余字段没有"对账"约束

涉及：backend/src/paylite/db/models.py:560-565

大白话

工资记录（payroll_record）上同时存了三样东西：属于哪个批次、哪个期间、哪个主体。但"批次"本身就已经写着它属于哪个期间和主体了。同一信息存两份，在数据库设计里叫反规范化——故意为之，为了让"按期间/主体汇总"不用多查一次表，这没问题。问题是：没有规则强制这两份信息一致。

解法：复合外键

-- 父表先声明一个"身份组合"约束
ALTER TABLE payroll_batch
  ADD CONSTRAINT uq_payroll_batch_scope UNIQUE (id, subject_id, payroll_period_id);

-- 子表的三个字段作为整体引用它 → 记录的期间/主体永远等于批次的期间/主体
ALTER TABLE payroll_record
  ADD CONSTRAINT fk_payroll_record_batch_scope
  FOREIGN KEY (payroll_batch_id, subject_id, payroll_period_id)
  REFERENCES payroll_batch (id, subject_id, payroll_period_id);
真实后果：某段代码单独改了记录上的期间没改批次 → 月底按期间汇总工资时，这笔钱出现在错误的月份，而且没有任何报错。
知识点：反规范化（denormalization）= 用冗余换查询速度，代价是要自己保证一致；复合外键（composite FK）= 让数据库替你"对账"。

#5 工资期间的校验有缝：月份和日期可以对不上

涉及：backend/src/paylite/db/models.py:264-266

大白话

payroll_period 表里有两组信息：year=2026, month=6 这样的数字，和 period_start / period_end 两个日期。现在的 CHECK 只保证了"period_start 是 1 号"，但没保证"period_start 的年月 == year 和 month 字段"，也没保证 period_end 是月末。

-- 现在：只查"是 1 号"
CHECK (EXTRACT(DAY FROM period_start) = 1)
-- → year=2026, month=6, period_start=2026-07-01 也能通过 ✗

-- 建议补上跨列一致性：
CHECK (EXTRACT(YEAR FROM period_start) = year
   AND EXTRACT(MONTH FROM period_start) = month)
知识点：CHECK 约束也能做跨列比较（同一行内的多个列互相校验）——很多人以为 CHECK 只能检查单列。"自然月"是这个系统的领域约定，约束应该把约定钉死在库层。

#6 文件指纹全局唯一，和"重复导入要提示用户"的产品规则冲突

涉及：backend/src/paylite/db/models.py:335 · CONTEXT.md（产品决策）

大白话

SHA-256 是文件的"指纹"——内容相同的文件指纹一定相同。现在数据库规定：这个指纹全系统只允许出现一次。而产品文档（CONTEXT.md）写的规则是："重复导入默认作为新批次保存并提示，由用户选择新增或更正。"两条规则打架了。

冲突场景：6 月上传过一次空的考勤模板，7 月又上传同一份文件 → 不是进入"提示用户选择"的流程，而是直接被数据库拒绝（报唯一约束错误）。产品预期里这是应该"提示后允许"的操作。

两种修法（先做产品决策再动手）

  • 按产品规则改约束的作用域：UNIQUE (payroll_period_id, import_type, file_sha256) —— 同一期间、同一类型内去重，跨期间允许；
  • 或承认"全局幂等"是有意设计（同一文件绝不导入第二次），把 CONTEXT.md 的说法改掉。
知识点：唯一约束有作用域：全局唯一 vs 分组唯一，选错作用域 = 把产品规则硬编码进了数据库；幂等（idempotent）= 同一操作执行多次和执行一次效果相同——全局指纹唯一其实是一种防重幂等设计，本身没错，但必须和产品流程对齐。

#7 用 psql 直接建表后，Alembic 会"失忆"并报错

涉及：backend/sql/001_initial_schema.sql · docs/database-design.md

大白话

Alembic 判断"数据库现在在第几个版本"，靠的不是看表结构，而是查库里那张 alembic_version 小表。用 psql 执行 SQL 文件建表时，这张表不会被创建——于是 Alembic 认为库还是空白，下次 upgrade head 会把所有表再建一遍，报"table already exists"。

psql "$PAYLITE_DATABASE_URL" -f backend/sql/001_initial_schema.sql
# 表建好了，但 alembic_version 不存在 → Alembic 以为一切还没发生

cd backend && alembic stamp head
# stamp = "别动手改结构，只在账本上把版本号标成最新"
# 打完 stamp 之后，upgrade head 才不会重复建表
知识点：stamp 和 upgrade 的区别——upgrade 真的执行迁移改结构，stamp 只改"账本"不动表。文档里两条初始化路径（psql 直执行 / alembic upgrade）并列，但必须补一句"走 psql 路径后要 stamp head"。

#8 .env 按相对路径找，换个目录启动就"静默失联"

涉及：backend/src/paylite/config.py:12

大白话

env_file=".env" 是相对路径。相对谁？相对你运行命令时所在的目录（CWD，概念⑥），不是 config.py 所在的目录。在 backend/ 里启动能找到；在仓库根目录启动就找不到——而且 pydantic 找不到不报错，静默跳过，用代码里写死的默认连接串。本地默认串恰好也能连上，所以你毫无察觉。

# 现在：跟着 CWD 走，随启动目录漂移
env_file=".env"

# 建议：锚定到 config.py 自己的位置，从哪启动都一样
from pathlib import Path
BASE_DIR = Path(__file__).resolve().parents[2]  # → backend/
env_file=BASE_DIR / ".env"
真实后果：你现在以为程序读的是 .env，实际可能读的是代码里的默认值。等部署到服务器、或者改了 .env 发现"怎么不生效"，才会暴露。
知识点：CWD（概念⑥）· Path(__file__) 是"以代码文件自身为锚点"的标准手法 · "静默失败"（fail silently）是最危险的失败方式——宁可启动时报错，也不要带着错误配置继续跑。

#9 future=True 是过时的开关

涉及：backend/src/paylite/db/session.py:12

是什么：SQLAlchemy 从 1.4 过渡到 2.0 时，提供了 future=True 让你提前用上 2.0 的新行为。项目现在用的就是 2.x，行为永远是"future"的，这个参数成了死代码。
知识点：这类"过渡期开关"要随版本升级清理掉，不是错误，是噪音——它让读者误以为还有"非 future"模式可选。

低

#10 外键列没有索引

涉及：backend/src/paylite/db/models.py:174,566 等（大量 FK 列）

是什么：PostgreSQL 声明外键时不会自动给外键列建索引（很多人以为会）。没有索引的后果：按这列查询慢（全表扫描）；删除/更新父表行时，数据库要全表扫描子表来检查引用。
为什么是低优先级：本机单人、数据量小，现在毫无感觉。知识点：惯例是"每个 FK 列手动配一个索引"，数据量上来之前先记账。

低

#11 部门树防了"自己当自己的爹"，防不了"循环收养"

涉及：backend/src/paylite/db/models.py:81-83

是什么：CHECK 约束只能看到当前这一行的数据。parent_id <> id 挡住了"部门的上级是它自己"，但挡不住"A 的上级是 B、B 的上级是 A"——每行单看都合法，整棵树却成了环。
知识点：跨行的规则（环检测）超出 CHECK 的能力，要用触发器或应用层递归检查。部门树是查询汇总的维度，成环会让递归查询死循环。

术语表

DDL（Data Definition Language）
定义结构的 SQL：CREATE TABLE、ALTER TABLE、CREATE INDEX。"默认值写进 DDL"= 默认值属于表结构本身。
迁移（Migration）
数据库结构的一次受控变更，像 Git commit 一样按顺序排列，可前进（upgrade）也可回退（downgrade）。
真源（Single Source of Truth）
同一事实只有一份权威定义。它的反面是"多份手工同步的副本"，问题 #1、#12 都源于此。
反规范化（Denormalization）
故意把同一信息存两份，换取更快的查询。代价：需要约束或触发器保证两份一致（问题 #4）。
幂等（Idempotent）
同一操作执行多次与执行一次效果相同。唯一约束是一种强制幂等的手段（问题 #6）。
排他约束（EXCLUDE Constraint）
PostgreSQL 特有：要求多行之间的某个"范围值"互不相交，UNIQUE 只能比相等，它能比相交（问题 #3）。
触发器（Trigger）
挂在表上、在 INSERT/UPDATE/DELETE 时自动执行的自定义函数，本项目用它实现了"工资锁定后不可变"。
CWD（Current Working Directory）
当前工作目录：你运行命令时所在的目录，相对路径都以它为基准（问题 #8）。
