# 轻算薪 PayLite — 项目决策与产品记忆

## 2026-09-15 业务决策确认（四轮合并）

本节为用户本轮确认的最新口径；与下文旧描述冲突时以本节为准。仅更新业务约定，尚未修改业务代码、数据库约束或迁移。

1. **整批更正**：确认后发现错误，生成整个原工资批次的新版本，重新确认批次内全体员工；不是仅替换出错员工。新版本生效后，期间汇总取该批次最新有效版本，旧版本保留追溯；独立补发不等同于更正。已实际发薪后的更正差额在线下处理，系统不自动生成下月补发或扣回。用户预期此类错误通常不会发生，但保留第一轮已确认的整批更正能力。
2. **薪酬结构与转正**：薪酬标准由固定薪资 80% 和绩效基数 20% 组成；试用期只有固定薪资、不考核绩效、不发绩效奖金，也无需绩效记录，同一员工转正前后固定薪资保持不变。转正当月绩效基数沿用已确认规则：整月采用转正后标准，实际绩效金额为该基数乘以当月绩效系数。普通员工加减薪按适用工资期间整月处理，不按月中操作日拆段。转正日期及算薪必需的薪资信息由员工维护页面提供。用户确认日折算采用当月自然日天数、变更当天按新标准；但此前 8,000 涨到 10,000 的例子只是折算示例，不代表本项目转正时固定薪资实际上涨。入离职、主体和部门调动的既有处理规则继续保留。
3. **整批校验门槛**：导入仍允许正确行先导入、错误行保留待修；试算允许展示部分员工结果，但工资批次全体员工必须全部通过校验，才能确认和正式导出。需考核绩效的员工缺系数、缺城市规则等错误不能通过只确认其余员工绕过。修复影响输入后需重新试算。
4. **全公司激励**：各主体数据未齐时可以先试算普通工资；考勤激励等待本期全公司数据齐全后统一计算。尚未包含最终激励的试算不是可直接确认的最终工资结果。按当前业务使用假设，不会在本月修改上月工资或扣款，不设计跨月更正上月扣款并联动已确认激励的流程。
5. **个税暂由人工处理**：个税计划后续手工计算，当前不增加系统复杂度，不新增系统个税计算或专门的个税回填流程。系统导出未扣个税的工资结果，用户在 Excel 中手工计算并扣税，核对后用于实际发薪，暂不回填系统。系统金额明确标识为“未扣个税金额”，不是最终实际到账金额；无来源税务字段留空并提示，不把未知税额解释为零。允许在已确认的整批校验门槛通过后导出供线下处理，缺个税不额外阻断该流程；导出文件在人工扣税核对前不视为可直接发薪的最终文件。
6. **试算失效**：薪资、考勤等影响计算的输入发生变化后，旧试算失效；必须重新试算并查看结果后才能确认，不允许继续确认旧试算。
7. **社保基数**：采用固定配置值，与员工薪资、试用期或转正无关，员工统一采用维护在城市基数中的值，具体数值后续输入。沿用按员工 base 地匹配城市的路径，不作员工薪资折算；这里统一的是缴费基数，不是直接固定每项缴费金额。
8. **公积金**：公积金以员工固定薪资为基数，个人、公司单边比例各为 5%，合计 10%；个人部分作为工资扣款，公司部分计入公司成本，不从员工工资扣除。固定薪资为薪酬标准的 80%，绩效不计入公积金基数。

## 1. 选定路线

**路线 C**：轻量、本地 / 自部署优先的中国算薪工具。

定位：**Excel 驱动的工资计算与结果导出工具**。

维护员工固定薪酬和绩效基数，导入每月考勤表、绩效表，按考勤、绩效、社保和公积金规则生成工资结果，填充工资表、代发工资表、人工成本表和正常工资薪金所得模板。系统不计算个税；无法取得的税务字段留空，并在导出报告中提示。

工作名：**轻算薪（PayLite）**。

## 2. 目标用户

中小企业 HR：

- 规模约 5–300 人
- Windows + Excel 使用习惯
- 无专职 IT 部门

## 3. 产品边界（明确不做）

- 不做一体化 HRMS（考勤 / 招聘 / 绩效等）
- 不接个税申报接口，只导出申报辅助格式
- 数据不出本机：本地存储、无账号、无云同步

## 4. 核心壁垒

按期间版本化的「城市社保基数 + 公积金规则 + 考勤薪酬规则」和对既有 Excel 模板的稳定适配。

## 当前范围澄清（2026-09-05）

第一阶段只服务一个目标公司。目标公司下有多个国内主体，用户暂将主体描述为分公司或分支机构，具体主体清单、主体类型和城市后续补充。

当前系统定位为工资数据管理与核对基础设施，不实现个税计算。工资明细由固定 Excel 模板导入；系统保留原始文件、模板版本、字段映射、逐行导入状态和错误信息，以及导入后的规范化数据。

已确认的导入与数据规则：

- Excel 采用固定模板，系统提供模板下载。
- 一次导入中，正确行可以先导入，错误行单独列出。
- 确认后的工资记录不可直接修改，错误通过更正批次处理。
- 当前只有单一使用者，不做复杂权限。
- 员工需要支持入职、离职、主体调动、部门调动、职位变化、工资变化、银行卡变化、社保和公积金城市变化。
- 部门体系在主体之间共用，但主体 A 与主体 B 可以各自有同名部门。
- 社保规则按员工 base 地匹配城市统一固定缴费基数；公积金按员工固定薪资计缴，个人和公司比例均为 5%。旧规则上下限字段仅作兼容，不改变已确认口径。

### 初步建模方向

建议将数据分成四类：

1. 公司与组织主数据：`company`、`subject`、`department`。
2. 人员与历史关系：`employee`、`employment` 或 `employee_assignment`。
3. 工资期间与工资事实：`payroll_period`、`payroll_batch`、`payroll_record`、`payroll_item`。
4. 导入与追溯：`import_batch`、`import_row`、`correction_batch`、规则/基数历史表。

最终表结构要等 Excel 一行的业务粒度、工资项目范围、主体准确含义和期间/批次规则确认后再锁定。

字段缺口、模板逐列映射缺口和未决业务规则详见 [工资系统字段缺口与未决规则](data-gaps.md)。

### 用户已确认的补充决策

- 主体先作为工资归属单位使用，不区分法律类型；主体类型暂记为分公司或分支机构，具体清单和城市后续提供。
- 员工以身份证号码作为业务唯一标识；当前只保留最新员工资料，不建立员工资料历史版本。
- 部门采用统一编码/名称体系，在不同主体下保留主体部门实例，并支持上下级结构。
- 查询支持工资期间、主体、部门、员工和导入批次，默认按主体和工资期间汇总。
- 实际社保、公积金基数按员工和工资期间保存。
- 导入正确行与错误行分开处理；错误行修正并重新校验通过后才进入正式台账。
- 已确认工资记录不可直接修改，需通过更正批次；重复导入保存为新批次并提示用户选择新增或更正。
- MVP 需要完成 docs 中四个 Excel 模板对应的输出能力；税务模板不计算个税，系统填充已有非税数据，其他没有来源的税务字段留空并在导出报告提示。

### 模板驱动的输出范围

当前 docs 中的模板显示，系统至少需要支持四类输出：

1. 人工成本按主体、部门和项目维度汇总的报表。
2. 按主体生成的代发工资文件。
3. 按主体和工资期间生成的工资表。
4. 正常工资薪金所得申报模板及其人员、扣除和金额字段。

其中第四类模板包含个税申报字段，而当前产品边界明确不实现个税计算。因此需要先决定它是仅导出已导入的外部结果，还是从 MVP 暂时移出；在该决定前，不应把 `tax_*` 字段误建成系统计算字段。

### 核心工资计算范围（2026-09-05）

系统维护每位员工的最新固定薪酬和绩效部分基数，每月导入考勤表和绩效表。绩效表提供系数，系统按“固定薪酬 + 绩效部分基数 × 绩效系数”生成实际月薪，再填充四个既有 Excel 模板。个税不计算；相关字段只填充外部提供的数据，否则留空并在导出报告提示。

考勤异常需要进入工资计算：迟到、早退、请假按固定薪酬折算，并区分有薪/无薪两种枚举；P7 及以上员工不参与任何考勤罚款，也不参与考勤激励分钱；忘打卡每次扣款 30 元；工资记录必须保存异常类型、扣款金额和来源。2026 年 7 月将所有主体合计的 2026 年 6 月考勤扣款金额，平均分给全公司 2026 年 7 月有考勤记录、无迟到早退忘打卡请假、已转正且职级低于 P7 的正式员工，分钱不区分职级；导出项目名称为“考勤激励”。

社保和公积金按员工 base 地匹配城市规则，由系统计算并保存结果，不设置人工结果对照。城市规则保存社保固定缴费基数、险种公司/个人比例及公积金固定薪资口径；新增公积金规则个人和公司比例均为 5%，旧上下限字段不作为隐式截断。

人工成本表只处理工资及相关成本字段，不处理其中的项目工时部分。

目前已看到一张按月、按员工展开的考勤表截图，包含期间信息、员工信息、考勤/工资汇总和每日明细；由于截图分辨率不足，具体列名和一行粒度仍以原始 Excel 文件为准，暂不据此锁定字段。


建议至少包含以下实体：

- `company`：目标公司。
- `subject`：工资归属主体。
- `department`：共用部门体系及主体部门实例。
- `employee`：员工主档，身份证号码唯一且不可修改。
- `employee_salary`：员工最新固定薪酬、绩效部分基数及生效信息。
- `payroll_period`：工资所属期间和实际发放日期。
- `payroll_batch`：主体、期间和发放类型组成的发放批次。
- `attendance_record`：员工期间考勤事实、异常类型、有薪/无薪枚举及原始导入值。
- `performance_record`：员工期间绩效系数及原始导入值。
- `social_security_rule`：城市、险种、期间有效的社保基数上下限和缴费比例。
- `housing_fund_rule`：城市、期间有效的公积金基数上下限和公司/个人比例。
- `employee_base`：员工按 base 地匹配的社保/公积金城市资料。
- `payroll_record`：员工、主体、期间、批次的工资结果快照。
- `payroll_item`：工资项目明细，包括考勤扣款、绩效、社保、公积金等。
- `import_batch` / `import_row`：原始 Excel、模板版本、字段映射、逐行状态和错误。
- `export_batch`：导出文件、模板版本、生成参数和结果提示。

工资结果以“员工 + 主体 + 工资期间 + 发放批次”为主记录，金额汇总默认按主体和工资期间查看。系统应保存输入快照、规则版本和计算明细，使同一期间能够解释每一个输出金额的来源。

### 已经确定

- 单一目标公司，多个国内工资归属主体；不做多公司和复杂权限。
- 系统输入为员工主档/最新固定薪酬与绩效基数、月度考勤表、月度绩效表。
- 实际月薪的主公式为：`固定薪酬 + 绩效部分基数 × 绩效系数`。
- 工资结果主粒度为：员工 + 主体 + 工资所属期间 + 发放批次；输出汇总默认按主体和工资期间。
- 四个 docs 模板全部需要输出，并保持工作表、表头、列顺序、合并、样式和正确公式；人工成本表不处理项目工时。
- 系统不计算个税；没有来源的数据留空，并在导出报告提示。
- 迟到、早退、请假按照固定薪酬折算：应出勤天数从考勤表读取，节假日、调休和加班由考勤表先处理；每日标准工时 8 小时，迟到/早退按分钟并使用同一公式，请假按天数计算；同日多个异常由考勤表先合并；有薪/无薪只用于请假，有薪假不扣固定薪酬、无薪假按天数折算；考勤表提供事实，系统统一重算扣款；P7 及以上员工不参与任何考勤罚款；忘打卡每次扣 30 元，补卡后免扣；异常类型和扣款来源需保留。
- 2026 年 7 月考勤激励是按月复用规则的首次实例：将上月所有主体合计的考勤扣款，平均分给本月有考勤记录、无迟到早退忘打卡请假、已转正且职级低于 P7 的正式员工，按符合条件人数平均分配且不区分职级；激励保留 2 位小数，尾差给排序最后一名；使用上月锁定后的扣款总额，无合格员工时不生成但提示，计入应发和实发且不计入社保公积金基数；导出项目名为“考勤激励”。
- 工资期间按自然月；每个主体每月一个正常工资批次，补发或其他发放使用独立批次，按期间汇总导出时合并到员工期间总结果。
- 转正前后固定薪资不变，转正当月绩效基数整月采用转正后标准；普通员工加减薪按适用工资期间整月处理。入离职、主体和部门调动继续按生效日期处理。
- 工资项目和最终结果保留 2 位小数并四舍五入，中间计算保留高精度；需考核绩效的员工若缺失系数则报错，不生成该员工正式工资结果；试用期员工无需绩效记录。
- 入职、离职或转正发生在月中时，社保和公积金按城市规则整月缴费，工资本身仍按生效日期分段折算。
- 社保按员工 base 地匹配城市配置的统一固定基数，与员工薪资无关，具体数值后续维护；缴费比例按城市规则计算。公积金以员工固定薪资为基数，个人、公司单边比例各为 5%，合计 10%；个人部分作为工资扣款，公司部分计入公司成本，不从员工工资扣除。固定薪资为薪酬标准的 80%，绩效不计入公积金基数。
- 员工以身份证号码作业务唯一标识，身份证号码不可修改；员工主表只保留当前资料，工资结果保存计算快照。
- 导入原始文件、模板版本、行级校验、错误信息和导出批次需要可追溯。

### 仍未理清且会影响部分实现

1. **工资日折算边界**：月中分段时的日数分母、零/负数工资和扣款超过收入的处理。
2. **考勤边界**：应出勤天数异常值、同日已合并异常的校验失败处理。
3. **考勤激励边界**：6 月考勤扣款项目范围、7 月主体变化时的归属、无合格员工时的处理已部分明确，规则长期复用方式仍待定。
4. **社保/公积金边界**：城市规则缺失或过期时的处理、base 地是否允许社保和公积金分开配置。
5. **批次与数据质量**：实际发放日期是否必填、状态流转、锁定后更正关联和期间汇总取值。

这些项目不阻塞数据库、输入模板、导入框架和导出框架的开发；计算规则可先通过配置接口和 fixture 测试实现。



## 8. 已确认技术方案（2026-09-12）

### 应用形态与运行方式

- 当前阶段以本地网页端运行，不做 PyInstaller、Windows 安装包或单个 EXE。
- 用户通过浏览器访问本机 Web 服务，默认使用 `127.0.0.1`。
- 前端由 Vite 提供开发服务；后端由 Uvicorn 启动 FastAPI。
- 数据库 PostgreSQL 运行在本机，数据不上传云端。
- 后续如需远程部署或多人访问，需要重新评估数据边界、账号认证、权限和备份方案。

### 技术栈

- 后端：Python 3.13、FastAPI、Uvicorn、Pydantic v2。
- 数据层：PostgreSQL、SQLAlchemy 2.x、Alembic、psycopg 3。
- 前端：React、TypeScript、Vite、Ant Design。
- 前端数据与表单：TanStack Query、React Hook Form。
- Excel：使用 `openpyxl` 处理 `.xlsx`；旧式 `.xls` 税务模板统一转换为 `.xlsx` 后作为运行时模板。
- 测试：pytest、Vitest、Testing Library、Playwright。
- 代码质量：Ruff；后续视需要加入 mypy。

### 数据实现约定

- 业务计算使用 `Decimal`，数据库金额使用 `NUMERIC(18, 2)`，不使用浮点数作为金额来源。
- 身份证号码、银行卡号等业务标识按文本保存。
- 使用 Alembic 管理 PostgreSQL schema migration。
- 导入原文件、模板版本、字段映射、行级错误、规则版本、工资计算快照和导出批次均需可追溯。

可复用的中国个税参考实现：

- `theajack/salary`（JS 累计预扣）
- `linglu/geshui`（Python 累计预扣）
- `beijing-salary-calc`（Vue 3）
