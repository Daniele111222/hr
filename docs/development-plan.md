## 事实基线和设计依据

当前代码包含应用工厂、健康检查、ORM、初始迁移、约束测试及后端 CI；尚无业务接口、算薪核心、Excel 适配器和前端工程。数据库中存在字段不等于对应业务已实现。

实施依据按以下职责使用：

- [领域上下文](../CONTEXT.md)和[产品决策](product.md)：以 2026-09-15 最新八条确认口径为准，覆盖与其冲突的旧描述。
- [后端架构](backend-architecture.md)：模块职责、事务、并发、快照与当前 schema 缺口。
- [数据库说明](database-design.md)：现有约束与迁移方式。
- [开发与 CI 工作流](development-workflow.md)：本地验证及 CI 门槛。
- Obsidian 的《PayLite 接口文档》《PayLite 数据表文档》作为已阅读的接口与数据模型参考；其中业务接口属于规划，旧版本示例不能覆盖最新决策。本任务计划在仓库内可独立阅读。

旧文档中的“社保按员工固定薪资计算”“普通调薪按操作日分段”“重复正常批次换批次号重试”等表述不作为实现依据。全系统展示与导出需明确“未扣个税金额”，不把未知税额默认为零。

## 实现约束

- 使用已确认的本地网页端技术栈；数据保留本机。远程部署、复杂权限、Windows 安装包、个税计算和专门回填流程不在本轮。
- API 负责 DTO 与错误映射；service 负责用例和事务；domain 使用规范化输入做纯计算；Excel 适配器负责格式。简单查询不强制套通用 Repository。
- 金额使用 Decimal；项目和最终结果四舍五入保留两位。身份证、银行卡和 API 金额遵循文本契约。
- 新 schema 需求使用新增 Alembic revision 和可审查 SQL，不改写初始迁移，不静默猜测既有记录的业务值。
- 规则变更、输入修正和公司期间激励变更必须参与试算版本校验；确认和导出不能使用过期结果。
- 确认后业务内容不可直接改写。更正通过整批新版本及受控替代机制实现，保留历史快照。
- 员工资料只维护当前信息和算薪必需的生效信息，不扩展完整历史档案；历史工资依赖计算时快照解释。
- 原始文件、模板版本、字段映射、行级状态、规范化输入、规则来源、计算步骤和导出结果需可追溯。
- 不等待真实员工数据或城市数值才开发；可使用明确标为测试用途的合成样例。真实数据用于后续配置与人工对账。

## 验证和完成标准

每项验收勾选必须有实际证据，不能用计划中的测试替代已运行结果。

- 后端：针对改动的 Ruff 与格式检查、实际模块依赖检查、编译检查、pytest；涉及持久化的功能执行 PostgreSQL 集成测试。每批交付执行既定后端 CI 与镜像构建，新增分层约束随真实模块落地。
- 集成测试只使用专用测试数据库及显式重置开关，不指向开发工资库。
- 前端：组件/表单测试覆盖校验与错误反馈；关键闭环使用 Playwright，最终执行生产构建。相应工具与命令随前端工程建立，不声称已有前端 CI。
- 计算：覆盖转正、调薪、入离职/调动、P7、请假补卡、规则缺失、精度和激励金额守恒。
- 状态：覆盖部分失败、旧试算拒绝、全员门槛、确认后不可变、并发/重试、更正切换和补发去重。
- 文件：实际检查四个工作簿的结构、样式、公式、扩行、文本标识和缺失字段；可打开文件不等于金额已核对。
- 每批稳定后按实际改动做规范与需求审查；最终跑通“输入—纠错—试算—激励—确认—锁定—四类导出—整批更正/补发—再次汇总”的闭环。
- MVP 整体验收包括人工样例对账；真实数据未到位时，明确区分合成样例通过和业务实数验收未完成。
